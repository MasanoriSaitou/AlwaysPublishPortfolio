# ソフトウェア移植指示書 (Migration Specification) ※例として「Python（Flask）から Go（Gin）への移植

## 1. 基本情報 (Overview)
*   **目的**: 既存の[移植元のシステム名/機能名]を、パフォーマンス向上と型安全性の確保のために、別のプログラミング言語へ移植・
              リプレイスする。
*   **移植元 (Source)**: Python 3.10 / Flask
*   **移植先 (Target)**: Go 1.22 / Gin Web Framework


## 2. 移植元の仕様と構造 (Source Environment)
添付されたZipファイル（`source_code.zip`）の概要は以下の通りです。
*   **主要な機能**: Users（ユーザー管理）と Items（商品管理）のCRUD操作を行うREST API。
*   **アーキテクチャ**: 簡易的な3層アーキテクチャ（Controller - Service - Repository）。
*   **データベース**: PostgreSQL (ORMとしてSQLAlchemyを使用)。
*   **認証方式**: JWTによるトークン認証（リクエストヘッダーの `Authorization: Bearer <Token>` から検証）。


## 3. 移植先の要件 (Target Environment)
移植先の実装では、以下の環境および構成を厳守してください。

### 3.1 ディレクトリ構成案 (Directory Structure)
Goの標準的なクリーンアーキテクチャに準拠した以下の構成にしてください。
```text``` 
.
├── cmd
│   └── api
│       └── main.go       # エントリーポイント
├── internal
│   ├── domain           # ドメインモデル（構造体定義）
│   ├── repository       # データベース操作 (SQLX または生SQL)
│   ├── service          # ビジネスロジック
│   └── handler          # HTTPリクエストハンドラ（コントローラー）
├── config               # 環境変数・設定読み込み
└── go.mod

### 3.2 技術スタック・ライブラリの指定
Web Framework: github.com/gin-gonic/gin
DB Driver / ORM: ORMは使わず、github.com/jmoiron/sqlx を使用して生SQLを記述すること。
JWT Library: github.com/golang-jwt/jwt/v5


## 4. コーディング規約・実装方針 (Coding Standard)
AIエージェントはコードを生成する際、以下のルールを必ず適用してください。

命名規則:
Goの一般的な慣習（関数名・構造体名はキャメルケース、外部公開するものは大文字開始）に従うこと。

エラーハンドリング:
例外（Panic）は発生させず、Goの標準的な if err != nil 形式で呼び出し元に明示的にエラーを返すこと。
ログ出力には標準の log パッケージ、または uber-go/zap を想定したラッパーを使用すること。

環境変数の管理:
DB接続情報やJWTのシークレットキーは、コードにハードコードせず、必ず環境変数（.envファイル経由）から読み込む構造にすること。

コードの省略禁止:

// TODO: 実装をここに書く や // 省略 といったコメントでのごまかしは一切禁止します。すべてのロジックを完全に記述してください。


## 5. 移行時の変更・リファクタリング要件
単なる直訳ではなく、以下の最適化を行ってください。

非同期処理の最適化: 移植元で同期処理（Blocking）になっていた外部API通信や重い計算処理は、移植先の言語の特性（Goであれば Goroutine /
 Channel）を活かした非同期処理、または並行処理に書き換えてください。

古い仕様の廃止: 移植元の utils/old_crypto.py にある暗号化処理は脆弱なため、移植先では標準の crypto/sha256 を使用した処理に
刷新してください。


## 6. テスト要件 (Testing)
各 service および handler のコードを生成する際は、対応するユニットテスト（単体テスト）のコード（例: *_test.go）もセットで
生成してください。

正常系だけでなく、異常系（バリデーションエラー、DB接続エラー、データ未存在）のテストケースを必ず含めてください。


## 7. APIの対比表（リクエスト・レスポンスのサンプル）
### 7.1 API仕様の維持要件
移植前後で、APIのエンドポイント、HTTPメソッド、リクエスト/レスポンスのJSONフォーマットは完全に一致させてください。
*   **例: ユーザー作成API**
    *   URL: `POST /api/v1/users`
    *   Request JSON: `{"name": "string", "email": "string"}`
    *   Response JSON: `{"id": 1, "status": "success"}`

### 7.2 外部システム・外部APIとの連携仕様
システムが「決済API（Stripeなど）」「認証基盤（Auth0など）」「社内別システム」と通信している場合、その仕様を明記します。AIはこれを読み飛ばすと、ダミーのコードで済ませてしまうことがあります。

*   **記載例:**
    ```markdown
    ### 外部連携仕様
    *   `services/payment.py` はStripe APIと通信しています。移植先でもStripeの公式SDK（Go用）を使用し、同様のAPIを叩く構造にしてください。
    *   外部通信のタイムアウト時間は一律「5秒」に設定し、コンテキスト（Context）でのキャンセルに対応させてください。

### 7.3 バリデーションルール
*   ユーザー登録時: 名前（必須、最大50文字）、メールアドレス（必須、Email形式）、パスワード（必須、8文字以上・英数字含む）
*   エラー時のレスポンス: `{"error": "エラーメッセージ"}` の形式で統一し、HTTPステータスは `400 Bad Request` を返すこと。

### 7.4 特殊なアルゴリズムや「泥臭い仕様」の解説
「なぜかここだけ特殊な計算をしている」「過去のバグ回避のために奇妙な条件分岐が入っている」という、いわゆる**レガシーコードの罠**が
ある場合、あらかじめ理由を書いておきます。AIが気を利かせて「不要なコード」として削除してしまうのを防ぐためです。

*   **記載例:**
    ```markdown
    ### 特殊なロジックについての注意
    *   `utils/calculator.py` 内の `calculate_tax` 関数で、特定の商材（ID: 999）だけ消費税計算を免除する分岐があります。
         これはビジネス上の仕様（例外ケース）なので、移植先でも必ず同じ分岐を再現してください。

### 8. 移植元の動作確認方法（エージェント用）
移植元の挙動やテストを確認したい場合は、以下のコマンドを実行してください。
*   依存解決: `pip install -r requirements.txt`
*   アプリ起動: `python app.py`
*   テスト実行: `pytest`
